# Implementation Plan: A-Spade Auto-play & Suit Following

**Branch**: `002-autoplay-suit-following` | **Date**: 2026-09-30 | **Spec**: [spec.md](./spec.md)

---

## Summary

Deliver the first active gameplay loop of Kazhutha. When the host starts the game, the player holding A♠ has it played automatically, establishing spades as the led suit. Players must then follow suit on each turn; the server enforces this with a dual-layer strategy (server authoritative, client pre-filters for UX). When all players in a round follow suit, the round resolves cleanly — cards are discarded and the highest-ranked led-suit card's holder leads the next round. This slice builds on Slice 1's lobby, dealing, and game table and extends them with a round state machine, a pure round-engine domain module, and new Socket.IO events.

---

## Technical Context

**Language/Version**: TypeScript 5.x (frontend and backend)

**Primary Dependencies**:
- Frontend: React 18, Vite, Tailwind CSS, Socket.IO client (all from Slice 1)
- Backend: NestJS, Socket.IO, `GameStoreService`, `GameService`, `DeckService` (all from Slice 1)

**Storage**: In-memory — `currentRound: RoundState | null` added to existing `GameRoom`. No new storage mechanism.

**Testing**: Vitest (frontend), Jest (backend)

**Target Platform**: Desktop browsers (Chrome, Firefox, Safari). Node.js 20+ on the server.

**Project Type**: Web application — React SPA + NestJS WebSocket server

**Performance Goals**: A♠ auto-play visible within 2 seconds of "Start Game" click. Round resolution and next-round broadcast within 1 second of last card played. State consistent across all clients within 1 second of any event.

**Constraints**: Desktop-only. No database. In-memory state only. Single Node.js process. Vett resolution out of scope — any player with no led-suit cards has all cards enabled (vett action is deferred to Slice 3).

**Scale/Scope**: Same as Slice 1 — up to 6 players per room, multiple concurrent rooms.

## Constitution Check

*Evaluated against [constitution.md](../../.specify/memory/constitution.md). Re-checked after Phase 1 design.*

| Principle | Status | Notes |
|---|---|---|
| I. Separation of Concerns | Pass | Pure game rule logic lives in `round-engine.ts` (stateless functions). `GameService` orchestrates. `GameGateway` handles I/O only. UI components derive display state from snapshot; no business logic in components. |
| II. Justified Modularity | Pass | `round-engine.ts` earns its existence: independently testable pure functions reused by `GameService` for auto-play, `play-card` validation, turn advance, and round resolution. No unjustified splits. |
| III. Encapsulated State | Pass | `currentRound: RoundState | null` is owned exclusively by `GameStoreService` via the `GameRoom`. `GameService` reads and replaces it atomically through the store. No module directly mutates `GameRoom` outside the store owner. |
| IV. Consistency | Pass | New event names follow kebab-case (`round-started`, `round-update`, `round-ended`, `play-card`). New types follow existing conventions (string-literal unions, camelCase fields). |
| V. Low Complexity | Pass | `round-engine.ts` functions are single-responsibility with cyclomatic complexity ≤ 2 each. `validatePlay` is the most complex — it chains 3 independent checks but branches do not nest. |
| VI. Clear Module Structure | Pass | New files placed in existing directories: `backend/src/game/round-engine.ts`, `backend/test/round-engine.spec.ts`. No new directories. Shared types in `shared/types.ts`. |

No violations. Complexity Tracking section not needed.
