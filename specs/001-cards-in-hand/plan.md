# Implementation Plan: Cards in Hand

**Branch**: `001-cards-in-hand` | **Date**: 2026-09-23 | **Spec**: [spec.md](./spec.md)

---

## Summary

Deliver the first playable state of Kazhutha: players open a browser, create or join a room via a short code, and see their own dealt hand of cards face-up while other players' hands appear face-down. This slice bundles the full project scaffold (React + Vite frontend, NestJS backend), real-time Socket.IO connectivity, card dealing logic, and the game table UI into a single deliverable.

---

## Technical Context

**Language/Version**: TypeScript 5.x (frontend and backend)

**Primary Dependencies**:
- Frontend: React 18, Vite, Tailwind CSS, Socket.IO client, `@heruka_urgyen/react-playing-cards`, `vite-tsconfig-paths`
- Backend: NestJS, `@nestjs/platform-express`, `@nestjs/websockets`, Socket.IO, `tsconfig-paths`, `tsc-alias`

**Storage**: In-memory (`Map<roomCode, GameRoom>`) — no database. State is lost on server restart; acceptable for this stage.

**Testing**: Vitest (frontend), Jest (backend, NestJS default)

**Target Platform**: Desktop browsers (Chrome, Firefox, Safari). Node.js 20+ on the server.

**Project Type**: Web application — frontend SPA + backend WebSocket server

**Performance Goals**: Lobby updates visible within 1 second of join event. Game table loads within 3 seconds of "Start Game". No measurable degradation with up to 6 concurrent players per room.

**Constraints**: Desktop-only layout (min 1280×720). No database. No auth. In-memory state only. Single Node.js process.

**Scale/Scope**: Up to 6 players per room, multiple concurrent rooms. Single-server, single-process.

## Constitution Check

*Evaluated against [constitution.md](../../.specify/memory/constitution.md). Re-checked after Phase 1 design.*

| Principle | Status | Notes |
|---|---|---|
| I. Separation of Concerns | Pass | Deck/deal logic lives in `DeckService` (pure, no Socket.IO). Gateway handles only orchestration. UI components handle only rendering. |
| II. Justified Modularity | Pass | Three modules: `GameModule` (store + logic), `RoomModule` (gateway + room events), shared types. Each has a single named responsibility. |
| III. Encapsulated State | Pass | `GameStoreService` is the sole owner of the `Map<roomCode, GameRoom>`. No global variables. Gateway accesses state only through the service. |
| IV. Consistency | Pass | All entities use string-literal union types (no enums). All event names kebab-case. All files kebab-case. camelCase for variables throughout. |
| V. Low Complexity | Pass | `dealCards`, `shuffleDeck`, and room code generation are single-responsibility functions with cyclomatic complexity of 1–2. Gateway methods delegate to services. |
| VI. Clear Module Structure | Pass | `shared/` → types only. `backend/src/game/` → store + logic. `backend/src/room/` → gateway. `frontend/src/` → components, hooks, socket layer. No circular dependencies. |

No violations. Complexity tracking section not needed.
